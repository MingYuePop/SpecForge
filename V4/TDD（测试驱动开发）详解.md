核心理念                                                                                                     
  TDD 的核心思想是：先写测试，再写实现代码。它颠覆了传统的"先写代码再测试"的开发顺序。

  经典三步循环：Red-Green-Refactor

  ┌─────────────────────────────────────────┐
  │                                         │
  │   🔴 Red → 🟢 Green → 🔵 Refactor     │
  │     ↑                        │          │
  │     └────────────────────────┘          │
  │                                         │
  └─────────────────────────────────────────┘

  1. Red（红灯）— 写一个失败的测试

  - 在写任何实现代码之前，先写一个测试用例
  - 这个测试描述了你期望代码具备的行为
  - 运行测试，确认它失败（因为还没有实现代码）
  - 失败是预期的，证明测试本身是有效的

  2. Green（绿灯）— 用最少的代码让测试通过

  - 编写刚好足够让测试通过的实现代码
  - 不要多写，不要提前优化，不要考虑"将来可能需要"
  - 目标是用最简单、最直接的方式让测试变绿
  - 此阶段允许"丑陋"的代码

  3. Refactor（重构）— 在测试保护下改善代码

  - 测试通过后，回头审视代码
  - 消除重复、改善命名、提取抽象、优化结构
  - 每次重构后重新运行测试，确保行为不变
  - 测试就是你的安全网

  然后回到第 1 步，开始下一个循环。

  ---
  一个具体例子

  假设要实现一个 add(a, b) 函数：

  第一轮循环：

  # Red — 先写测试
  def test_add_two_numbers():
      assert add(1, 2) == 3  # 此时 add 函数还不存在，测试失败

  # Green — 写最少的代码
  def add(a, b):
      return a + b  # 测试通过

  # Refactor — 代码已经很简洁，无需重构

  第二轮循环：

  # Red — 增加新需求的测试
  def test_add_negative_numbers():
      assert add(-1, -2) == -3  # 运行，发现已经通过了

  # 继续增加边界测试
  def test_add_floats():
      assert add(0.1, 0.2) == pytest.approx(0.3)

  ---
  TDD 的关键原则

  ┌──────────────────────────────┬──────────────────────────────────────────────┐
  │             原则             │                     说明                     │
  ├──────────────────────────────┼──────────────────────────────────────────────┤
  │ 不写没有对应测试的生产代码   │ 每一行实现代码都必须由一个失败的测试驱动出来 │
  ├──────────────────────────────┼──────────────────────────────────────────────┤
  │ 只写刚好让测试失败的测试代码 │ 编译不过也算失败，一次只关注一个行为         │
  ├──────────────────────────────┼──────────────────────────────────────────────┤
  │ 只写刚好让测试通过的生产代码 │ 抵制过度设计的冲动                           │
  └──────────────────────────────┴──────────────────────────────────────────────┘

  ---
  TDD 的优势

  1. 高测试覆盖率 — 代码天生被测试覆盖，因为代码就是为了让测试通过而写的
  2. 更好的设计 — 为了可测试，代码自然走向低耦合、高内聚
  3. 即时反馈 — 几秒内就知道改动是否破坏了已有功能
  4. 活文档 — 测试就是最准确的需求说明，永远与代码同步
  5. 重构信心 — 有完善的测试保护，大胆重构不怕回归
  6. 减少调试时间 — 问题在引入的当刻就被发现

  TDD 的常见挑战

  1. 初期速度变慢 — 前期写测试感觉多花了时间，但后期维护成本大幅降低
  2. 测试粒度把握 — 测试太细导致重构困难，太粗则失去保护作用
  3. UI/数据库等外部依赖 — 需要用 Mock/Stub 隔离，增加复杂度
  4. 团队习惯转变 — 需要纪律和练习

  ---
  TDD 的变体

  - ATDD（验收测试驱动开发）：从用户验收标准出发写测试，粒度更粗
  - BDD（行为驱动开发）：用自然语言（Given-When-Then）描述行为，强调沟通
  - Outside-In TDD（伦敦学派）：从外层（API/控制器）向内层推进，大量使用 Mock
  - Inside-Out TDD（底特律学派）：从核心领域逻辑开始，逐步向外构建，少用 Mock

  ---
  总结

  TDD 的本质不是"测试技术"，而是一种设计方法论。它通过"测试先行"迫使开发者在写代码前先思考清楚：

  这段代码应该做什么？它的输入输出是什么？它与外部的边界在哪里？

  这种思维方式带来的设计质量提升，往往比测试本身更有价值。
