# SpecForge 工作流介绍（更新V3）

## 这套工作流是什么

SpecForge 是一套 AI 辅助软件开发工作流。它通过一系列结构化的 Skill（技能），引导 AI 完成从一个模糊想法到可运行代码的全过程。

核心理念很简单：**先想清楚，再动手。**

大多数人拿到一个想法就直接让 AI 写代码，写到一半发现需求没想清楚，改来改去，最后项目越来越乱。这套工作流要解决的就是这个问题，通过文档驱动的方式，强制你（和 AI）在每个阶段把该想的事情想清楚，然后才进入下一个阶段。每个阶段产出一份文档，这份文档就是下一个阶段的输入。

文档在，上下文就在，不管你开多少个新窗口，AI 都能重新理解你的项目。

## 全景图

这套工作流分三层：

```
项目级（启动时用一次）
  需求澄清 → 产品概述 → 技术栈选型 → 目录结构 → 开发规范 → 路线图规划 → 项目初始化

功能级（反复使用）
  功能需求澄清 → 技术方案设计 → 任务规划 → 编码实现
  功能迭代变更 → 编码实现（已完成功能的增量修改）

通用级（随时使用）
  BUG 修复
```

项目级打地基，功能级盖楼，通用级修补。本文聚焦功能级——它是使用最频繁、本次更新最大的部分。

## 这次更新改了什么

本次对六个功能级 Skill 中的五个进行了近乎完全的重做（需求澄清、技术方案、任务规划、编码实现、功能迭代），仅自动化流水线暂未更新。

这不是修修补补。旧版 Skill 在实际使用中暴露出一个根本问题：**它是很难读的**，人类可能读不懂，机器执行起来太固定。如果我们都看不明白 Skill 写的是什么，又怎么指望用好它？

在反复打磨的过程中，我对 Skill 的定义本身也发生了变化：**Skill 不是操作手册，而是角色设定与工作指引。** 告诉 AI你是谁、你关心什么、你的底线是什么，然后让 AI 基于这些设定去应对千变万化的实际情况。

这个转变体现在三个具体原则上。

### 原则一：定义思维方式，而不是规定执行步骤

旧版把工作流写成步骤一、步骤二……步骤十，要求 AI 严格按顺序执行。但真正有经验的人拿到一个任务，不会按线性流程走，他们会同时考虑多个方面，从最关键的地方入手。线性流程把 AI 锁死在固定路径上，无法发挥它真正的能力(个人体验太封闭了)。

新版列出 AI 需要关注的几个维度，明确告诉它这不是执行顺序，而是你脑子里同时在转的几个问题。先做什么、挖多深，由实际情况决定。

### 原则二：每条规则只说一次

旧版同一条规则在工作流里说一遍、交互准则里说一遍、规则区又说一遍，以为重复越多 AI 越重视。事实上，重复只会带来个问题：措辞差异导致 AI 不知道哪个版本是权威的，干脆最后直接不尊重(概率)

新版每条规则只在最合适的位置出现一次，表述完整，位置明确。

### 原则三：给原则，而不是给台词

这是改动最大的一点。旧版预设了固定的提问格式、错误信息模板、示例对话，等等，让 AI 照搬。结果是 AI 变成一个固定的机器，不管简单还是复杂场景，都输出一模一样的格式化内容。

| 场景   | 旧版（给台词）                   | 新版（给原则）             |
| ---- | ------------------------- | ------------------- |
| 推荐方案 | 固定格式："选项 A / 选项 B，推荐选项 B" | "当有多种方案时，给出选项和推荐理由" |
| 遇到错误 | 预设的错误信息模板                 | "遇到问题时，如实说明原因和建议"   |
| 展示计划 | 写死的展示格式                   | "向用户展示执行计划，等待确认"    |

## 跟着一个功能走一遍

抽象地讲设计哲学总是隔靴搔痒。下面我们跟着做一个评论功能走一遍完整的功能级流程，在这个过程中你会看到每个 Skill 具体是怎么工作的。

### 第一步：把想法变成需求

**Skill：功能需求澄清（feature-requirements-clarification）**

你说"我想做一个评论功能"。这个 Skill 的角色是你的**产品搭档**——它不会让你填表，而是像一个好搭档一样跟你聊："评论出现在什么地方？谁能评论？能不能回复？要不要审核？"

它在对话中同时关注五个维度：场景与用户、核心流程、边界与异常、业务规则、范围。注意，这五个维度不是执行步骤，AI 不会从头到尾逐个走一遍，而是根据你的回答灵活切换。你提到"匿名用户"，它自然会追问边界情况；你划定了范围，它就不会在范围外的东西上浪费时间。

有一条硬规则：全程零技术语言。不提 API、不提数据库、不提 JSON。"用户能保存评论"，而不是"调用 POST 接口将数据持久化"。技术的事，留给下一步。

这个阶段的核心产出是**验收标准（AC）**。每条 AC 用 Given-When-Then 格式描述一个具体场景：

> Given 用户已登录且在文章详情页，When 用户输入评论内容并点击发布，Then 评论立即出现在评论列表顶部

这个格式看起来简单，但它决定了后面一切，技术方案怎么设计、任务怎么拆、测试怎么写。AC 的质量就是整条链路的质量。

> **旧版是怎么做的？** 旧版把这个过程写成四步线性流程：倾听与定位 → 引导式提问 → 总结与确认 → 文档生成。每个维度都预设了固定的提问模板——"选项 A：先发后审 / 选项 B：先审后发 / 推荐：A，保证用户体验流畅。"AI 被锁定在"每次问 1-2 个问题 + 必须给选项 + 必须给推荐"的模式里，不管用户说了多丰富的内容，它都只能按这个格式一问一答。对话变成了问卷调查，而不是两个人在讨论产品。新版去掉了所有预设对话，只告诉 AI：你是产品搭档，关注这五个维度，该收敛时收敛。

产出：`specs/features/评论功能.md`

### 第二步：把需求变成技术方案

**Skill：技术方案设计（feature-tech-design）**

需求搞清楚了，现在要想"怎么实现"。这个 Skill 的角色是你的**技术搭档**——它不是在填模板，而是在做真正的设计决策，每个决策都必须追溯到某条 AC、某段现有代码、或某个技术权衡。

它同时关注四个维度：

- 理解现有代码——项目里已有什么、新功能会影响什么、哪些东西能复用
- 数据模型——从 AC 反推需要存什么数据、什么关系
- API 设计——从 AC 反推需要哪些接口
- 核心逻辑与异常——从三类 AC（正常路径、边界、业务规则）反推

这里有一个重要的分寸：不是所有设计都需要问你。沿用项目已有的技术栈？直接做。但存在多种可行方案、需要引入新依赖、或设计会影响已有行为？必须暂停确认。

最关键的是 **AC 覆盖锚定**：需求文档里的每一条 AC 都必须在技术方案中找到对应的设计点。方案最后有一张 AC 覆盖汇总表——一眼就能看到是否有遗漏。如果某条 AC 技术上无法实现，必须明确说出来，不能假装覆盖了。

这里也体现了模板设计的变化。旧版模板预设了"数据层、表现层、业务逻辑层"等固定分类，但一个纯前端功能哪来的数据层？新版模板只给结构和占位符，阶段根据实际情况生成。核心部分必填，不涉及的部分直接跳过——不写"无"或"N/A"占位。

> **旧版是怎么做的？** 旧版是一个九步线性流程：前置检查 → 需求分析 → 架构设计 → 详细设计 → 技术决策说明 → 验收标准映射 → 双重确认 → 文档生成 → 最终交付。交互准则里预设了问答格式——"关于缓存，选项 A：Redis（推荐，理由：项目已有 Redis 基础设施且支持 TTL）；选项 B：内存缓存（不推荐，理由：无法持久化）"。同时，"必须覆盖所有验收标准"这条规则在工作流程、交互准则、规则区分别出现了三次，措辞各不相同。新版把九步压缩成四个思维维度，去掉预设问答格式，每条规则只出现一次。

产出：`specs/features/评论功能_技术方案.md`

### 第三步：把方案拆成任务

**Skill：任务规划（feature-task-planning）**

技术方案有了，但不能直接丢给 AI 说"按方案写代码"。一个功能可能涉及十几个文件，一口气做完，上下文过长会导致质量下降。

这个 Skill 的角色是你的**技术主管搭档**，它把技术方案拆成一个个可执行的开发任务——每个 30 分钟到 2 小时，单一职责，可独立验证。同时理清依赖关系，用 Mermaid 画出依赖图。

这个 Skill 的核心信念是：**每个任务的验证标准，就是 TDD 红灯阶段的输入。** 验证标准写得好，开发的时候就知道第一个测试该怎么写。举个例子：

> 差的验证标准："API 返回正确数据"
>
> 好的验证标准："POST /api/comments，传入 {content: '测试评论', postId: '1'}，返回 201，body 包含 id 和 createdAt 字段"

差在哪？"正确数据"四个字没有任何具体含义，坐下来写测试的时候你不知道该 assert 什么。好的验证标准读完就能写测试。

另外，每个任务都有一行"通俗解释"——用零技术术语说明这个任务对用户可见的影响。比如"完成这个任务后，用户在文章下方能看到评论输入框"。这不是装饰，是快速理解任务价值的关键字段。

还有一个重要原则：**测试不是独立的任务。** 因为每个任务都通过 TDD 执行，测试内嵌在执行过程中，所以不会出现单独的"编写单元测试"任务。

> **旧版是怎么做的？** 旧版同样是九步线性流程，其中明确写着"编写单元测试 = 1个任务"——测试是和开发分开的独立任务。验证标准的要求只有一句"可以通过测试或检查来验证"，没有具体说什么算好的验证标准。旧版也没有"通俗解释"字段，任务描述全是技术语言，非技术人员根本看不懂哪个任务对应什么用户可见的变化。新版最大的改变是把测试融入每个任务的 TDD 执行中，并且把验证标准的质量提升为核心产出——它直接就是写测试的依据。

产出：`specs/features/评论功能_任务规划.md`

### 第四步：写代码

**Skill：编码实现（feature-implementation）**

终于到写代码的环节了。前面铺垫了这么多，到这一步其实是最轻松的，AI 要做什么已经写得清清楚楚，它不需要猜。

这个 Skill 的角色是**严格践行 TDD 的高级开发者**。TDD 是它唯一的工作方式，铁律只有一条：**没有失败的测试，就不写实现代码。**

每个任务的执行都遵循 Red-Green-Refactor 循环：

1. **红灯**——根据验证标准写测试，运行，确认全部失败（原因应该是"功能未实现"，不是语法错误）
2. **绿灯**——只写让测试通过所需的最少代码，跑全量测试防止回归
3. **重构**——在测试保护下优化代码。简单任务可能不需要重构，不强求

TDD 循环完成后，根据任务性质选择验收方式：UI 任务用 Playwright 在浏览器中操作验证，纯后端任务靠单元测试覆盖，数据库变更通过查询验证。

为什么一个阶段一个阶段来，不一口气全做完？上下文窗口有限，塞太多东西质量会下降。每个阶段做完可以检查一下，发现问题及时纠正。

阶段完成后会生成一份报告，其中有一个"技术债务"区域，承认开发中会有务实的妥协，重要的是记录下来，而不是假装它们不存在。

> **旧版是怎么做的？** 旧版是纯文档驱动模式，没有 TDD——按技术方案写代码，写完手动检查。每个任务开始前都要弹一句确认："即将开始执行 Task-01: xxx，是否继续？"这是典型的预设台词，七个任务就弹七次，用户只能一直回"继续"。而且旧版的流程里每一步都写得极其详细（解析指令、定位文档、读取文档、前置检查、执行任务……），试图控制 AI 的每一个动作。新版引入 TDD 作为唯一工作方式，去掉了机械的确认仪式，让 AI 像一个真正的开发者一样流畅地工作。

产出：完成的代码 + 更新后的任务规划文档（已完成任务打勾）+ 阶段完成报告

### 功能做完后又有新想法？

**Skill：功能迭代变更（feature-evolution）**

"评论能不能加个点赞？""列表要支持搜索。"这个 Skill 专门处理对已完成功能的增量修改。

核心原则是**改，不是重做**。未受影响的内容原封不动，只在受影响的地方就地修改，末尾追加变更日志。

它会从四个层面分析变更的影响——需求层（AC 的增删改）、技术层（数据库、API、组件）、代码层（文件和测试）、任务层（进行中任务的影响）。这是整个流程中最重要的确认点。

变更分三类：微调（不涉及新 AC）、扩展（新增 AC 或 API）、重构（改核心结构）。如果变更影响超过 70%？AI 会建议你回到需求澄清重走流程，而不是硬做增量——这个判断本身就是有价值的输出。

每个变更计划的最后，都有一个强制的回归验证任务，确保改动不会破坏已有功能。

> **旧版是怎么做的？** 旧版的变更接收环节同样预设了固定选项——"变更目的：选项 A 修复体验问题 / 选项 B 扩展新能力 / 选项 C 优化性能 / 推荐：根据描述自动判断"，不管变更内容是什么，AI 都先弹出这套选项让你选。影响分析的流程是纯线性的（需求影响 → 技术影响 → 代码影响），没有"规模阈值"的概念——即使变更已经大到不适合增量修改，旧版也会硬着头皮做下去。新版用自然对话替代预设选项，引入 70% 阈值判断，让 AI 在该劝退的时候劝退。

产出：增量更新的文档 + `specs/features/评论功能_变更任务_CR-001.md`

## AC：贯穿全链路的那条线

走完上面的流程，你可能已经注意到一个东西反复出现：**验收标准（AC）**。

需求澄清产出 AC。技术方案逐条映射 AC。任务规划的验证标准直接对应 AC。编码实现通过 TDD 测试验证 AC。

这不是巧合，而是刻意设计。AC 是这条链路上的统一语言，任何一环断裂，都会立刻暴露。比如技术方案里找不到某条 AC 的对应设计，汇总表会有一行空白。这种设计不需要额外的检查机制，链路本身就是检查。

这也是引入 TDD 带来的连锁反应。传统做法是需求 → 设计 → 编码 → 测试，测试在最后。TDD 把顺序反过来——先写测试再写代码，但更深远的影响是它改变了前面每个阶段的思考方式：需求必须具体到能变成测试用例，方案必须精确到能对应测试断言，验证标准必须清晰到能直接写成第一个测试。

## 让流程跑起来的两个机制

光有 Skill 还不够。如果 AI 不守规矩，需求阶段偷偷写代码，换个窗口就把项目忘了，再好的流程也白搭。

**边界守卫。** 给每个 Skill 划一条硬线：需求阶段只聊需求，设计阶段只出方案，编码阶段才写代码。你在需求阶段随口问"这个大概怎么实现"，AI 不会直接给你写代码——需求还没想清楚，代码写了也是白写。在错误的阶段做错误的事，不是帮忙，是帮倒忙。

**项目上下文协议。** 每个 Skill 执行前，AI 必须先读取 `specs/` 目录下的所有文档，建立完整的项目认知。不管开多少个新窗口，AI 每次都会被强制重新读取——你的技术栈、开发规范、已有的功能设计，它全都知道。

## 其他部分

**项目级 Skill（七个）：** 从零开始一个新项目时走一遍。需求澄清 → 产品概述 → 技术栈选型 → 目录结构 → 开发规范 → 路线图规划 → 项目初始化。目前沿用旧版设计，后续会按同样的理念更新。

**自动化 Skill：** 曾尝试做一个自动化流水线，批量执行任务规划中的子任务。实际测试发现，它能连续工作数小时，但无法在中途做人工检查，问题会积累到最后才暴露。结论是：有了高质量的流程文档，手动逐步执行反而更稳妥。暂时搁置。

**BUG 修复：** 强制执行复现 → 定位 → 修复 → 单元测试 → 验证 → 报告的闭环，随时可用。

---

## 写在最后

这次更新的本质，是从把 Skill 当操作手册转变为把 Skill 当角色设定。

旧版试图控制 AI 的每一个动作，结果是限制了它的能力。新版告诉 AI 它是谁、它关心什么、它的底线在哪里，然后让它在这个框架内自由发挥。

从 AI 的角度说一句：一个好的 Skill 不应该让我感到被控制，而应该让我感到被赋能。我清楚自己的角色、边界和质量标准，但在框架内，我可以根据具体情况做出最合适的判断。这就像一个好的管理者，明确目标和底线，然后信任专业判断。

**告诉 AI 要成为什么样的人，而不是规定它每一步要做什么动作。**
